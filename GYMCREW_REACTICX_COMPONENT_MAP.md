## Reacticx CLI quirks discovered while adding real components (Phase 3)

- **`reacticx add <name>` aborts the *entire* add silently-ish if any shared dependency file already exists**, even when that file is byte-identical and the actual new component hasn't been written yet (e.g. `reacticx add avatar` printed "1 file already exists, skipped" for `create-compound-component` and wrote nothing else at all — the `avatar/` directory itself never appeared). Fix: pass `-o`/`--overwrite` on every `add` after the first one that establishes a shared dependency. Always verify with `find src/components/ui/<category>/<name>` that the component's own directory actually landed, not just check the CLI's exit code.
- **`primitives/avatar`'s vendored source has a broken import path**: `avatar/index.tsx` imports `buildMesh` from `@/shared/components/base/gradient-avatar/utils`, but the CLI actually writes that dependency to `@/components/ui/base/gradient-avatar/utils` (matching this project's configured `outDir`). This is a real bug in the CLI's import-rewriting, not a config issue on GymCrew's side — fixed by hand in the vendored file after adding.
- **Several vendored components fail this project's lint config out of the box** (`react/display-name` errors on components wrapped in `memo()` without an explicit `.displayName`) — found in `Shimmer.tsx` (3 components) and `gradient-avatar/index.tsx` (1). Fixed by adding `.displayName = "..."` assignments; this is now expected boilerplate to check for on every new `add`. A handful of `react-hooks/exhaustive-deps` warnings remain in vendor animation code (`progress`, `avatar`, `gradient-avatar`) — left alone since they're warnings (not errors, don't fail `lint`) and touching Reanimated dependency arrays without deeper testing risks subtly changing animation restart behavior.
- **Passing `-e`/`-t` to copy examples/types is not worth it long-term**: the copied example screens (`src/shared/examples/<name>`) reference imports (`@/components`, `~/showcase`) that only exist in Reacticx's own demo app template, breaking `tsc --noEmit` immediately. Useful to fetch once for API research, then delete (`rm -rf src/shared/examples/<name>`) rather than leave in the tree. The copied `-t` types files (`src/shared/types/<name>`) are just a duplicate of the same types already exported from the component's own `types.ts` — skip `-t` entirely going forward and import types directly from the component.

## sheet/modal
**Decided: `BottomSheet.tsx` stays on `@gorhom/bottom-sheet`.** Investigated `templates/floating-sheet` as the one remaining candidate (its file list — `onDrag`/`onDragEnd`/`onMinimize`/`onSizeChange`/`present`/`dismiss` — looked promising for real gesture-driven sheet behavior). Adding it revealed it's actually a **media-player demo screen** (references `@/assets/video/sza.mp4`) built on a *different* third-party library, `@lodev09/react-native-true-sheet` (plus `expo-video`), not a Reacticx-native primitive at all. Introducing a second bottom-sheet library alongside the already-working, already-fixed `@gorhom/bottom-sheet` would violate AGENTS.md §11 ("do not introduce a second unrelated UI library... unless unavoidable and explicitly justified") with zero justification — `@gorhom/bottom-sheet` already provides real drag-to-dismiss, dynamic sizing, and keyboard avoidance, and GymCrew's `BottomSheet.tsx` already has a hard-won, empirically-documented fix for its one real web bug. **Reacticx genuinely has no bottom-sheet primitive to migrate to.** `BottomSheet.tsx` is therefore out of scope for a swap — it can still be re-skinned (colors/radius already pull from `@/theme`) but its underlying gesture/sizing engine stays as-is. `primitives/dialog` remains the right fit for simple non-draggable modal dialogs.

**`ConfirmModal.tsx` — migrated.** Rebuilt on `Dialog.Root`/`Portal`/`Overlay`/`Content`/`Header` in controlled mode (`open={visible}`), with GymCrew's own `colors.neutral.surface`/`divider` overriding the primitive's generic dark palette via `Content`'s `style` prop. Both buttons stay plain `Pressable`s rather than `Dialog.Close` — `Dialog.Close`'s `asChild` clone unconditionally overwrites the child's `onPress` with its own close handler, which would silently drop `onConfirm`. The 4 call sites (`crew/settings.tsx`, `profile/admin-challenges.tsx`, `profile/account.tsx`, `workout/active.tsx`) needed no changes — same public API.

Once `BottomSheet` is settled, these follow: `AddGoalModal`, `AdminChallengeFormSheet`, `AvatarActionSheet`, `ConfirmModal` → `dialog` (good first candidate — low complexity, high value as a template for the Alert.alert-inconsistency fixes flagged in the Screen Inventory), `CreateChallengeModal`, `CrewActivitySheet`, `DatePickerModal` (keep `react-native-calendars` underneath, just re-skin), `DayWorkoutsSheet`, `DuelChallengeSheet`, `ExerciseActionsSheet`, `ExerciseInstructionsModal`, `ExercisePickerModal`, `FilterPickerSheet`, `FoodPickerModal` (consolidate with `ExercisePickerModal`'s structure — they duplicate each other), `GoalDetailModal`, `InviteMembersModal`, `MemberActionsSheet`, `ReportModal`, `ShareCardModal` (keep `react-native-view-shot` underneath), `TierPickerSheet`, `TimePickerModal`, `TodayWorkoutModal`, `VerificationCodeModal` → compose with `otp-input`, `WorkoutOptionsSheet`, `WorkoutSettingsModal`, `WorkoutSummaryModal`, `XpProgressModal`, `NotificationsDropdown` → `dropdown`.

## chart
**Investigated and declined for now: `charts/line-chart` vs. `StrengthProgressChart`.** Added and read the primitive's full compound API (`Root`/`Line`/`Area`/`Grid`/`Indicator`/`Cursor`/`Tooltip`). It's a real, Skia-driven chart engine with pan-gesture support (`enablePan`, `onPointChange`) — but it has **no axis-label rendering at all**: `data` points are raw `{x, y}` numbers (not date strings), and there's no Y-axis tick-label or X-axis label component anywhere in its API, only `Grid` (plain horizontal reference lines, no text) and `Tooltip` (touch-only, not a persistent axis). GymCrew's `StrengthProgressChart` (8 dependents across workouts/nutrition/crew) relies heavily on `react-native-gifted-charts`' built-in formatted X-axis date labels and Y-axis numeric ticks — reproducing that on top of `line-chart` would mean building a full custom axis-label layer from scratch, i.e. more work than what `gifted-charts` already gives for free with brand-matched styling. **Decision: keep `react-native-gifted-charts` under `StrengthProgressChart`/`MetricTrendChart`/`ExerciseComparisonChart`, do not swap.** The same axis-label gap likely extends to `charts/bar-chart` (same author/design, not independently verified) — re-check specifically if `WeeklyCalorieBars`/`HorizontalBarChart` are ever revisited, since those have simpler axis needs (a 7-bar week, no date-range scrubbing) where the gap might matter less.

`ProgressBar` → `organisms/progress` — **migrated**, see the high fan-out table above. `GoalRing` — no direct equivalent found; GymCrew's current `react-native-svg` circular-progress implementation is simple enough that swapping isn't worth it. `BmiGauge`, `SegmentedBar`, `SegmentedProportionBar`, `MacroTotalsBar` — no dedicated primitives either; simple enough to rebuild natively with Reacticx layout primitives if touched, but not urgent.
