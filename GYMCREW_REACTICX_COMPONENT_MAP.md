**Corrected gap analysis vs. what GymCrew needs**:
- ✅ **Charts exist** (`charts/bar-chart`, `line-chart`, `pie-chart`, `radar-chart`, `radial-chart`) — the earlier draft's claim that no chart component exists was wrong. These are real migration candidates for `StrengthProgressChart`/`MetricTrendChart`/`ExerciseComparisonChart`/`WeeklyCalorieBars`, to be evaluated in Phase 3 for feature parity (min/max range filters, dual-series comparison, area fill) against `react-native-gifted-charts`, which GymCrew currently uses.
- ❌ **No dedicated bottom-sheet/drawer component in the real registry** — this is the opposite of what the docs-site pass suggested (which listed `bottom-sheet`/`bottom-sheet-stack`). The closest primitives are `dialog` (primitives) and the `floating-sheet` template (a full scaffold, not a composable low-level component). **This changes the plan for `BottomSheet.tsx` (11+ direct dependents, the single highest-risk component in this codebase): it most likely stays on `@gorhom/bottom-sheet` under the hood, re-skinned with Reacticx's motion/pressable primitives around it, rather than being swapped for a Reacticx sheet component that doesn't exist.** Re-verify with `reacticx info dialog` and `reacticx info floating-sheet` at the start of Phase 3 before committing to this.
- Still no generic `card` component, though `pieces/profile-card` and several `blocks/*` sections may cover specific card shapes.
- `primitives/list` exists and is worth evaluating for GymCrew's various row-list screens (crew roster, food log, notifications) in Phase 3.
- Text input: `base/animated-input-bar` and `base/otp-input` remain the closest fits; no plain multi-line labeled TextField primitive.
- Still no calendar or camera component — `react-native-calendars` (under `DatePickerModal`/`NutritionCalendar`) and `expo-camera` (under `PhotoCaptureGuide`/`scan-barcode.tsx`) stay as-is, re-skinned only.
- Some registry names are capitalized inconsistently (`Toast`, `Pagination`, `Shimmer` vs. lowercase-hyphenated everywhere else) — confirm exact `add` slugs work as listed before scripting any bulk install in Phase 3.

## Recommended migration order (component layer, Phase 3)

1. `ConfirmModal` → `primitives/dialog` (low risk, fixes the documented Alert.alert web bug everywhere it's adopted)
2. `ProgressBar` → `organisms/progress` (highest fan-out, low complexity)
3. `Stepper` (no direct Reacticx equivalent found — check `molecules/range-slider`/`molecules/seek-bar` for a numeric-input pattern to borrow from), `FormField` → `base/animated-input-bar` (canonical input primitives, high reuse)
4. `Skeleton`/`HomeSkeleton` → `molecules/Shimmer`
5. `AvatarStack` → `primitives/avatar` (no dedicated `avatar-group` in the real registry — compose from `avatar` + overlap styling, same as today)
6. Investigate `charts/line-chart` and `charts/bar-chart` against `StrengthProgressChart`/`WeeklyCalorieBars` for feature parity — decide keep-vs-swap before touching any chart-heavy screen
7. `BottomSheet` — **first confirm via `reacticx info dialog`/`reacticx info floating-sheet` whether either is a viable base**; if neither fits, keep `@gorhom/bottom-sheet` and re-skin only, since ~15+ components depend on this one decision
8. Everything else, screen-by-screen per the phased plan in `GYMCREW_REACTICX_MIGRATION.md`

Branded/bespoke visuals (`MuscleHeatmap`, `RankBadge`, `DivisionBadge`, `BadgeRevealFx`, etc.) are never "migrated to Reacticx" in the sense of being replaced — they get their surrounding chrome (padding, shadows, pressable states) rebuilt on Reacticx primitives while the branded asset/animation core stays untouched.
